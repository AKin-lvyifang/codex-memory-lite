# Sync Policy

## 写入长期记忆

满足任一条件：

- 项目当前状态或下一步改变。
- 用户确认了会影响未来工作的决定或约束。
- 活跃 Task 开始、暂停、恢复、完成或改变范围。
- 新增了后续需要复用的文件、测试、提交、命令或外部来源入口。
- 丢失后会造成明显返工。

## Skip

- 普通解释、闲聊和重复信息。
- 尚未确认的脑暴方向。
- 没有后续价值的失败尝试。
- 完整工具输出、内部推理和可从真实文件直接重建的冗余内容。

`skip` 仍需写理由和来源 event ID，成功提交后才允许清理对应 pending。

`decisions.md` 与 `refs.md` 采用保留式更新：旧决定失效时追加替代说明，不能删除原记录。`current.md` 与 `brief.md` 才承担覆盖当前状态的职责。

## Unresolved

- 用户新说明与代码、测试、文档或既有决定冲突。
- 无法确定目标 Task。
- 架构、安全、不可逆操作或跨项目归属不清。
- 来源不足，无法确认事实。

Curator 不猜测，交给主 Agent。

## 第二遍检查

Curator 生成候选文件内容后，必须在同一轮中重新检查全部来源事件：

1. 每个来源 event 是否被候选覆盖。
2. 每个候选是否有明确 disposition 和理由。
3. 每个 `write` 是否都返回了白名单内的完整文件内容。
4. `skip` 是否只是无价值或重复信息。
5. 是否仍有应标记为 unresolved 的冲突。

Curator 只返回严格 JSON。`apply-result` 再验证路径、来源覆盖和真实文件变化，并生成 `sync-plan.json` 与 `coverage-report.json`；Curator 不能自行宣布校验通过。
